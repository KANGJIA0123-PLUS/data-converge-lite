# 状态库每日压缩备份与老化

正常运行的服务默认每天保存一份 SQLite 一致性备份并压缩，归档保留 30 天。活动的 `state.sqlite3` 继续使用；本功能不删除其中的成功记录、`UNKNOWN`、未完成任务、历史隔离记录或迁移审计。

## 配置与运行时机

```yaml
state:
  directory: /srv/its/MindOpsBOSE/data-converge/data/lite-state
  archives:
    enabled: true
    retention_days: 30
```

省略 `archives` 时使用以上默认值。`enabled` 必须为布尔值，`retention_days` 必须为正整数。调整归档开关或期限不改变任务定义、SQL 版本和部署绑定，不需要执行配置迁移。

只有正常服务完成启动检查后才启动归档维护。后台最多间隔 60 秒检查是否到达下一次维护时间，健康情况下按进程有效系统时区每天维护一轮：当天没有有效归档时创建一份；同日重启先验证并复用已有归档。下一轮按本地日期的午夜安排，夏令时切换日可以为 23 或 25 小时。失败后等待 5 分钟重试。服务停机期间不会执行维护，恢复后仅创建当天快照，不补造停机期间每天的快照。一次性执行、状态查询及诊断命令不启动维护。

容器时区由容器内 `TZ` 或系统时区文件决定；建议部署时明确设置 IANA 名称，例如 `TZ=Asia/Shanghai` 或 `TZ=UTC`，并确保对应时区数据可用。应用首次解析后固定有效时区，改变容器时区需重启服务；没有独立的 `scheduler.timezone` 配置项。当前为调测期，本轮不包含旧账本的时区迁移。

每日归档放在状态目录的同级目录。例如上面的配置对应：

```text
/srv/its/MindOpsBOSE/data-converge/data/
  lite-state/state.sqlite3        # 活动账本
  lite-state-archives/            # 每日压缩备份、维护状态
  configuration-backups/         # 配置迁移或旧账本恢复前备份
```

每日归档以 `daily-<UTC生成时间>-<唯一标识>.sqlite3.gz` 命名。目录权限为 `0700`，归档文件为 `0600`。快照使用 SQLite 一致性备份接口，包含已提交到 WAL 中的内容；不能用直接复制运行中数据库文件的方法替代。后台使用独立只读连接，分批备份、分块压缩并校验，归档完成后原子发布。

维护还会回收专属每日归档目录中满 24 小时、可确认属于本流程中断遗留的临时文件。独占的临时快照只在确认当天有效备份后清理；中断留下的重复硬链接可以先合并，并保留对应完整文件。不清理未知文件，也不扫描共享 `configuration-backups` 目录中的临时文件。

## 保留期限和迁移备份

每日归档按文件名中的原快照生成时间计算保留期。期限为 `retention_days × 24 小时`；压缩、重启不会重置计时。每轮先确认当天有效归档，再清理超过期限的旧文件。因此维护未运行或备份失败时，实际保留时间可能超过 30 天。30 天是清理期限，不是保证磁盘上永远恰好有 30 个文件。

默认 `configuration-backups` 中的迁移备份也参与维护：

- 只有当前账本的配置迁移审计明确引用、且名称符合本程序生成格式的文件才会被处理。
- 创建满 24 小时后压缩成原路径加 `.gz`；压缩和校验成功后才删除对应原文件。
- 按迁移审计中的原备份时间计算保留期，超过期限后清理。
- 其他账本的备份、未知文件、符号链接以及默认目录外的自定义 `--backup-dir` 文件不自动处理。

迁移审计里的 `backup_path` 保持原值。例如审计仍为 `.../abc.sqlite3`，实际可用文件可能已变为 `.../abc.sqlite3.gz`。这保留了操作发生时的事实；诊断会补充当前文件去向。超过期限后删除备份不会删除活动账本中的迁移记录或历史执行事实。

## 诊断与维护失败

```bash
bash /opt/its/data-converge/bin/start_data_converge.sh \
  --diagnose --format json
```

`state.archives` 检查项展示开关、保留天数、归档目录、最近归档时间、有效系统时区、维护状态和近期迁移备份的可用位置。“当天”与后台维护使用相同的系统本地日期，归档文件名中的生成时间保持 UTC。迁移备份状态含义如下：

| 状态 | 含义 |
| --- | --- |
| `original` | 原 SQLite 备份文件可用。 |
| `compressed` | 原文件已压缩，`path` 给出当前 `.gz` 路径。 |
| `expired_or_missing` | 受管备份已超过保留期且文件缺失，可能已由老化清理；仅凭缺失不能证明删除原因。 |
| `missing` | 文件缺失且不能按已到期解释，应核对维护日志和挂载。 |
| `unmanaged` | 文件不在自动维护范围，例如外部自定义备份目录。 |

诊断只检查文件是否为常规文件和维护状态，不对大归档重新解压校验，不创建目录或文件，不执行清理。归档不存在、维护状态不属于当天、维护失败等显示 `WARN`；设置无效显示 `FAIL`；关闭归档显示 `SKIP`。`PASS` 表示维护报告与文件存在情况正常，不替代实际恢复演练。

备份、压缩或清理失败时，服务记录固定错误码并在后续周期重试，汇聚调度继续运行。失败不会把未完成的压缩文件当作成功备份；未验证当天有效备份时不进行到期清理。维护中发现活动数据库丢失或被替换时，立即中止本轮维护和到期清理。排查时重点核对磁盘空间、目录权限、状态卷和归档维护日志。关闭服务或失去写租约时会取消维护，先结束维护线程，再释放账本写锁。

## 恢复边界

`.sqlite3.gz` 解压后是某一时刻的本地执行账本，可在独立位置执行 SQLite 完整性检查、读取历史记录或用于恢复评估。它不是 ClickHouse、Redis 与 SQLite 三者同时回到同一时刻的完整备份。

不要直接覆盖运行中的 `state.sqlite3`，也不要同时运行原账本和恢复出的副本。恢复前需停止使用该账本的所有实例，保留当前现场，并核对备份之后可能已提交的 SQL、`query_id`、临时租约配置与状态初始化标记；否则旧账本可能把已经执行的窗口当成待执行窗口。永久账本身份校验已临时移除，不应将“启动成功”视为恢复历史完整的证据，见 [DC-STATE-001](known-issues.md#dc-state-001)。具体恢复方案应依据现场证据确定，归档维护不自动回滚业务。
