# 第一阶段保留的业务与运行限制

第一阶段聚焦启动、解密、连接、调度及执行状态，保留原有52个SQL及字段合同。只修复：

1. `task_resource_5min_ads.sql` 的固定历史时间改为 `{start_time:DateTime}` / `{end_time:DateTime}`。
2. `task_resource_server_day_ads.sql` 重复的E2E count表达式删除，INSERT/SELECT恢复70列对齐。

以下已在原公司源码审查中确认，**本阶段未批量重写**。本地流程测试通过不等于这些统计值正确，投入业务报表前需逐项验收。

| 任务/字段 | 尚未迁移的修正 |
|---|---|
| 模型指标实例小时DWS的平均并发、参考吞吐率 | 跨时间桶直接SUM会放大，需区分组内/跨组与时间维度聚合 |
| 模型指标实例小时累计快照、直方图快照 | 外层argMax可能只留下一个逻辑组，需明确跨组快照合并 |
| 模型指标实例小时节点数组 | 组内先选一个node_id/ip会丢失跨节点TP拓扑 |
| 资源服务ADS | 服务按node_ips展开后再聚合可能在同一资源池重复累加完整服务指标 |
| 资源卡使用比例 | active/(active+used)与上游active/used口径不一致 |
| 健康状态NULL | 5分钟比例与异常计数的NULL规则不同，跨粒度结果不一致 |

未引入迟到数据重算；一个窗口确认成功后不会自动更新，源数据晚到需另行设计补算。没有业务表DDL迁移/自动建表/源数据去重；原SQL中的全限定数据库、表引擎和字段类型需现场核验。

本地锁只约束同一状态文件。没有Redis/Kubernetes租约，没有跨节点自动故障切换。账本和已有目标数据必须一起保全；本阶段没有自动清理历史账本、指标对账或未知写入自动恢复框架。

默认切换从新完整5分钟窗口开始，小时/日/月跳过跨切换点的部分窗口，等待首个完整周期。已有业务数据不能仅因记录缺失就重新INSERT。

DWD 消费等待全部五类信号，缺失只告警，不用 cron 强行执行半窗。生产者采用 best-effort 通知，因此“DWD 已写成功但信号没送达”需核验后补发；消费者不能凭空恢复缺失事实。Redis 必须与生产者使用同一端点、数据库和队列，并由本服务独占消费，详见 [就绪消费说明](dwd-ready.md)。

HTTP(S) 查询设置绝对 I/O 截止时间，但操作系统同步 DNS 查询不能被 Python 强制中断；解析返回后不会继续发送已过期查询。Redis 配置有限的连接/读取超时和轮询预算，Cluster 的拓扑发现仍可能包含多个 I/O，同样不承诺 DNS 的硬实时截止。公司 XMS SDK、原生依赖、Redis 拓扑和实际表结构尚未在本机验证。
