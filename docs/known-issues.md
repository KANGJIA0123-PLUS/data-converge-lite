## DC-STATE-001

**问题：Pod 替换后的状态连续性与重复写入防护仍未完整闭环；共享 Redis 状态、fencing 与接管重跑已实现。**

- 状态：**部分解决**；2026-11-06 双实例真实环境演练验证了共享状态、fencing 和中断窗口接管重跑，BUG-1、BUG-2、BUG-3、BUG-6 已修复并在真实环境复测，BUG-4 仍待部署配置，BUG-5 仅完成 CLI 提示与排队缓解、跨节点队列仍未解决；跨 Pod 完整持久账本和生产验收未完成。
- 优先级：高，影响替换 Pod 后的恢复和汇聚结果一致性。
- 范围：正常启动、维护写入、配置迁移、旧配置的新窗口恢复、选主诊断，以及双实例接管、共享状态导入、补算和滚动重启。
- 证据：[双实例真实环境演练报告（2026-11-06）](evidence/dual-instance-lab-2026-11-06.md)。该演练用两个独立状态目录模拟两个节点的 hostPath，走生产调度、租约、fencing、共享状态和执行器路径；独立状态目录不等同于生产环境共享持久账本验收。

### 现场触发与已确认事实

2026-10-19 19:53，更新镜像或重建 Pod 后，应用先取得 Redis 临时租约，随后因 `LEADERSHIP_LEDGER_MISMATCH` 退出。新 Pod 的本地账本身份为 `1cda34cf6121449d8154ecc510acaed5`，Redis 保存的原账本身份为 `a3f4f3c90e2c47e9b6c568ad530ced8e`；本地覆盖起点为当天 19:45。

身份不一致已确认。现场尚未确认具体卷类型、旧卷去向或挂载变更，所以不能把“原卷已丢失”当作已证实根因。Pod 名称变化本身不是账本身份；完整持久卷正常复用应能延续历史。现有设计通过永久注册拒绝身份不同的账本，却没有提供满足现场要求的跨 Pod 状态接续方案，导致这类替换持续阻断服务。

### 本次临时措施

1. 删除正常执行、迁移和旧配置恢复中基于 `leadership_cluster` / `leadership_ledger_id` 的身份判断，不再生成或绑定新的选主账本身份。
2. 删除 Redis 永久 `data_converge:leader:{cluster_name}:ledger` 的校验与注册调用。新版不读取、写入或删除该键；旧本地身份元数据也保留，便于现场追溯。
3. 保留临时选主租约、续租、失租停止新派发，以及同一物理账本的本地文件锁。它们承担当前写入协调职责，不证明历史连续。
4. 诊断报告 `ledger_identity_enforced=false`；本地检查仅报告当前选主配置，在线检查仅观察临时持有者是否存在和 TTL，不再以旧身份差异报错。
5. 正常服务启用选主时输出 `LEADERSHIP_LEDGER_CHECK_DISABLED: issue=DC-STATE-001`。这是明确记录临时措施的 WARNING，不是启动失败；有效临时租约及其余检查通过后仍可正常调度。

2026-10-19 的措施只解除选主账本身份限制，当时仍保留配置指纹、配置快照与 SQL 版本检查、覆盖起点、历史隔离、状态库缺失/损坏检查。2026-10-20 调测期间又临时关闭启动配置差异与缺库阻断，范围见 [DC-STATE-002](#dc-state-002)。回滚旧镜像或滚动更新期间混用版本时，旧程序仍可能执行原有身份校验并拒绝接管；新版不会为了兼容旧程序重建或改写注册。不能把删除本地元数据或 Redis 注册项当成回滚步骤。

### 已实现：共享 Redis 状态、fencing 与接管重跑

在 `leadership` 与 `dwd_ready` 均启用时，`redis_state` 把调度游标、任务实例终态、DWD 就绪事实和运行中实例写入同一个 `{cluster}` hash tag 下的 Redis 键。每次写入先由 Lua 比较当前租约 token：旧主失去租约后不能再覆盖新主状态（`REDIS_STATE_FENCED`）。新主接管时导入共享状态，已成功窗口不重跑；旧主遗留的 RUNNING 窗口记入本地 `orphan_queries`，接管方先 `KILL QUERY ... SYNC` 并轮询 `system.processes`，确认旧 query 已停止后才重跑；ClickHouse 不可达时只保持阻断、不盲目重跑，窗口显示 `PREVIOUS_QUERY_STILL_RUNNING:<query_id>`。补算派发也已把 RUNNING 发布到共享状态，避免“清理已执行、INSERT 中断、账本仍显示 SUCCESS”的旧问题（BUG-3）。

演练结果（S1、S2、S3、S8）显示：kill -9 后约 9 秒完成接管，中断窗口 KILL 后重跑；冻结/断网旧主被 fencing 后释放资源、回到备机等待；DWD 信号无丢失。BUG-1、BUG-3 修复后复测 S1c、S2b、S7b，重复/清空窗口均恢复为正确行数；全量测试与既有 50 个失败基线一致，无新增失败。完整证据见[双实例真实环境演练报告](evidence/dual-instance-lab-2026-11-06.md)。

这仍不是完整的跨 Pod 状态方案：共享 Redis 只保留配置的 TTL 内的游标、实例终态和 DWD 事实，不包含本地审计、UNKNOWN 处理记录、长期历史或本地补算队列；也没有 ClickHouse 端 fencing 或 SQLite 与 ClickHouse 的共同事务。

### 尚未解决的边界

- **完整持久账本仍是历史连续性的前提：** 共享 Redis 只保存 TTL 内的调度游标、实例终态和 DWD 事实，不能替代本地账本。整个状态目录及初始化标记缺失时，首次启动仍可能从当前五分钟边界创建新账本；旧的长期历史、UNKNOWN 处理记录、审计和本地补算队列不会自动回来。超过共享保留期的窗口也不能依赖 Redis 恢复。
- **独立账本或共享状态丢失仍可能重复写入：** 共享状态和 fencing 在保留期内可避免已成功窗口重跑、阻止旧主写状态；但 Redis 数据丢失、TTL 过期、`cluster_name`/命名空间变更或使用不同租约时，不同账本仍可能在不同时间重复处理同一业务窗口。
- **SQLite 存储保障：** 本地文件锁只协调相同物理文件；两个独立 hostPath 各有自己的锁，共享 Redis 不能替代账本存储。把 SQLite 文件放在共享目录也不自动保证锁、同步和故障恢复语义，需对目标存储进行验证。双实例演练使用独立状态目录，只验证协调与接管路径，不等同于生产共享账本验收。
- **下游写入边界：** Redis 租约、fencing 和接管前的 KILL/确认只能降低并发重跑风险，不能撤销已经发送的 ClickHouse INSERT，也不能恢复被部分写入的窗口；现阶段没有数据库端 fencing，也没有 SQLite 与 ClickHouse 的共同事务，不能宣称 exactly-once。UNKNOWN 仍需人工核对。
- **配置及选主命名空间变更：** 配置变化的临时放行范围见 DC-STATE-002。关闭选主或切换命名空间后，不同实例可能不再竞争同一租约，应先停止原写实例，临时解除不是多写部署支持。

### 后续修复方向与验收条件

共享状态、fencing 和接管重跑已经落地，后续重点转为完整持久状态、进程级恢复以及补算/运维边界。仍需首先确定可跨 Pod 连续使用的持久状态来源：经过目标环境验证的持久卷，或能支持事务、历史查询及租约协调的共享状态后端。接管应能区分完整历史、落后副本和全新状态，并显式报告恢复范围及无法确认的窗口；不能仅用共享 Redis 的短 TTL 数据代替完整账本。业务窗口的稳定写入身份、目标表幂等策略和数据库端防过期写者机制仍需结合实际 ClickHouse 表引擎、物化视图与写入方式验证，不能只增加 query_id 或去重参数就承诺不重复。

关闭本遗留项前至少需要以下验收证据（括号内为当前进展）：

1. 同节点及跨节点替换 Pod，完整持久状态可延续，成功窗口不重放，UNKNOWN 仍保留核查。（部分：跨实例协调和接管已有演练；演练使用独立状态目录，完整持久账本未验证。）
2. 滚动更新、强杀、租约超时与网络分区时，不产生未受控的双写；验证已提交 SQL 的收尾行为。（部分：fencing 未出现双主，BUG-1 重复写竞态、BUG-2 进程退出、BUG-6 结果分类已修复；BUG-4 终止预算仍需部署配置。）
3. 挂载空卷、落后备份、独立账本时能明确识别历史缺口，并按批准的恢复策略处理；不能用“进程启动成功”代替恢复成功。（未完成：共享 Redis 的 TTL 数据不能重建更早历史，空卷仍会创建新账本。）
4. 重复接管及恢复步骤可重入，对相同业务窗口的多次提交不会重复累计，且下游验收包含真实表引擎和依赖。（部分：成功窗口不重跑、中断窗口确认后重跑已复测；补算队列仍是本地文件（BUG-5），数据库端 exactly-once 未实现。）
5. 目标持久存储的锁、同步、磁盘满与断连恢复经过验证；备份后已写入的窗口在恢复时得到核对。（未完成：SQLite/共享存储故障语义未验证；Redis 断连已不再导致进程退出。）
6. 诊断同时展示当前任务进度、历史连续性和协调状态，三者不会混为一个 PASS；保留现有查询与执行审计。（部分：镜像状态和冲突已有查询入口；备机 CLI 仍可能展示过期本地数据，在线诊断无法确认租约持有者。）

双实例演练和本地回归验证了共享状态、fencing、接管重跑及 BUG-1/BUG-3 修复，测试失败集合与既有基线一致；它们不替代以上生产环境验收，也不覆盖尚未解决的 BUG-4、BUG-5。

## DC-STATE-002

**问题：调测期间临时关闭启动配置差异与缺库阻断，持久状态及配置接续方案尚未完成。**

- 状态：未解决；2026-10-20 按用户要求临时关闭相关启动校验，并允许手动删除数据库后重新初始化。
- 优先级：高，影响配置升级、历史连续性与汇聚结果一致性。
- 范围：正常启动时的部署绑定、当前配置及 SQL 与保存快照的差异检查，以及初始化标记存在但数据库缺失的处理。
- 关联：[DC-STATE-001](#dc-state-001) 记录跨 Pod 状态连续性和重复写入问题；本项没有解决这些问题。

### 现场信息与判断边界

现场报错涉及当前配置与已有状态的差异，用户为继续调测要求先移除相关启动限制，并要求手动删除 DB 后可以重新初始化。此要求是临时处理策略，不代表旧配置与当前配置已核对一致，也不代表删除数据库能够恢复执行历史。

现场日志中的任务数量为 56，而当前仓库配置预期为 60，说明现场所用包、挂载配置与当前仓库之间存在需要核对的不一致。任务数量本身不能断定现场一定使用旧镜像，也不能据此还原旧账本的配置；后续需核对实际镜像摘要、包内任务定义、运行时配置挂载及 SQL 文件。

### 本次临时措施与保留边界

1. 正常启动不再仅因部署绑定不符，或当前配置及 SQL 与已保存的有效快照不同而拒绝启动；`--init-state`、`--run-once`、`--run-task` 和 `--resolve-instance` 对此同样临时放行，已有覆盖起点和每任务有效起点仍约束执行。原绑定、快照和执行历史保留，已有的无快照旧账本自动恢复流程保留。日志与诊断明确提示校验临时关闭，并关联本遗留项；诊断的差异为 WARN，匹配时可为 PASS，但均附 `binding_enforced=false` 和 `configuration_enforced=false`，不表示检查策略已恢复。
2. 初始化标记存在但数据库已被手动删除时，允许取得本地锁后重新创建状态库，不再由缺库检查阻断。残留的 SQLite `-wal`、`-shm` 和 `-journal` 文件移入状态目录内的 `.state.sqlite3.orphans.*` 目录保留，避免误用于新库；该目录不是已恢复的历史。诊断查询保持只读，不负责创建、修复或恢复数据库。
3. 保留同一物理账本的本地锁、临时 Redis 选主租约、续租及失租停止新派发。当前配置仍须能够有效加载，已有数据库的损坏、结构及必要状态完整性检查仍保留。
4. 本轮不自动执行数据库删除、不恢复旧数据库内容，也不根据缺失记录推定窗口成功或自动补算。配置迁移与历史恢复工具的明确操作边界，仍需与正常启动的临时放行区分。

删除 DB 后创建的是新账本。原成功记录、UNKNOWN、任务尝试、调度游标、就绪信号、配置审计和积压窗口不会自动恢复；默认启动从新初始化的覆盖起点开始处理，旧窗口不会因此补算。数据库外已经写入的业务数据仍然存在，新账本无法据此判断哪些旧窗口已完成。若后续扩大覆盖范围、恢复过旧备份或重新提交旧窗口，仍可能重复写入。

临时放行配置差异也不证明旧游标、待处理实例和当前任务定义兼容，不能把旧任务按新 SQL 执行的结果视为已经过迁移核验。历史实例的依赖解释应继续检查证据是否匹配，无法确认时明确说明，不凭当前配置重建旧事实。

调度时，已移除任务、窗口定义变化或早于任务有效起点的旧待处理记录会保留并跳过，输出 `PERSISTED_WINDOW_SKIPPED`，不再让这些记录阻止当前任务执行；旧游标按当前 cron 规则重新对齐。跳过的记录并未完成汇聚，后续仍需核查和处理。

既有初始化边界也需统一：无配置快照的旧账本中，`--init-state` 只检查原覆盖起点非空，未完整验证其时间格式；无效值可能得到 `INITIALIZED`，但正常启动和诊断仍会失败。初始化结果不能替代正常启动与诊断验证，本轮未扩展该旧路径。

## DC-STATE-003

**问题：共享状态冲突需要人工核对并留下处置证据。**

- 状态：已解决；冲突支持 OPEN、RESOLVED、IGNORED 三种状态和受控处置命令。
- 优先级：中，影响冲突记录的长期维护，不阻断接管。
- 范围：`mirror_conflicts`、`--status` 和 `--diagnose` 展示的本地 SUCCESS 与共享终态差异。
