# 已知问题与后续处理

## DC-STATE-001

**问题：Pod 替换时的状态连续性与重复写入防护尚未完整实现。**

- 状态：未解决；2026-10-19 按用户要求先移除账本身份阻断，后续另行设计持久状态与恢复方案。
- 优先级：高，影响替换 Pod 后的恢复和汇聚结果一致性。
- 范围：正常启动、维护写入、配置迁移、旧配置的新窗口恢复，以及选主诊断。

### 现场触发与已确认事实

2026-10-19 19:53，更新镜像或重建 Pod 后，应用先取得 Redis 临时租约，随后因 `LEADERSHIP_LEDGER_MISMATCH` 退出。新 Pod 的本地账本身份为 `1cda34cf6121449d8154ecc510acaed5`，Redis 保存的原账本身份为 `a3f4f3c90e2c47e9b6c568ad530ced8e`；本地覆盖起点为当天 19:45。

身份不一致已确认。现场尚未确认具体卷类型、旧卷去向或挂载变更，所以不能把“原卷已丢失”当作已证实根因。Pod 名称变化本身不是账本身份；完整持久卷正常复用应能延续历史。现有设计通过永久注册拒绝身份不同的账本，却没有提供满足现场要求的跨 Pod 状态接续方案，导致这类替换持续阻断服务。

### 本次临时措施

1. 删除正常执行、迁移和旧配置恢复中基于 `leadership_cluster` / `leadership_ledger_id` 的身份判断，不再生成或绑定新的选主账本身份。
2. 删除 Redis 永久 `data_converge:leader:{cluster_name}:ledger` 的校验与注册调用。新版不读取、写入或删除该键；旧本地身份元数据也保留，便于现场追溯。
3. 保留临时选主租约、续租、失租停止新派发，以及同一物理账本的本地文件锁。它们承担当前写入协调职责，不证明历史连续。
4. 诊断报告 `ledger_identity_enforced=false`；本地检查仅报告当前选主配置，在线检查仅观察临时持有者是否存在和 TTL，不再以旧身份差异报错。
5. 正常服务启用选主时输出 `LEADERSHIP_LEDGER_CHECK_DISABLED: issue=DC-STATE-001`。这是明确记录临时措施的 WARNING，不是启动失败；有效临时租约及其余检查通过后仍可正常调度。

2026-10-19 的措施只解除选主账本身份限制，当时仍保留配置指纹、配置快照与 SQL 版本检查、覆盖起点、历史隔离、状态库缺失/损坏检查。2026-10-20 调测期间又临时关闭启动配置差异与缺库阻断，范围见 [DC-STATE-002](#dc-state-002)。回滚旧镜像或滚动更新期间混用版本时，旧程序仍可能执行原有身份校验并拒绝接管；新版不会为了兼容旧程序重建或改写注册。不能把删除本地元数据或 Redis 注册项当成回滚步骤。

### 尚未解决的边界

- **空卷或不同账本带来的历史断档：** 整个状态目录及初始化标记都缺失时，现有首次启动流程无法区分新部署和历史丢失，可能从当前五分钟边界创建新账本。旧成功记录、UNKNOWN、游标、就绪事实和历史积压不会自动回来。
- **独立账本接管可能重复写入：** 新账本或过旧备份不知道其他账本已完成的窗口。即使 Redis 先后只允许一个持有者运行，也不能阻止不同账本在不同时间重复处理同一业务窗口。
- **SQLite 存储保障：** 本地文件锁只协调相同物理文件；独立 hostPath 不能共享执行事实。把 SQLite 文件放在共享目录也不自动保证锁、同步和故障恢复语义，需对目标存储进行验证。
- **下游写入边界：** Redis 租约和 SQLite 提交不能撤销已经发送的 ClickHouse INSERT；现阶段没有数据库端 fencing，也没有 SQLite 与 ClickHouse 的共同事务，不能宣称 exactly-once。
- **配置及选主命名空间变更：** 配置变化的临时放行范围见 DC-STATE-002。关闭选主或切换命名空间后，不同实例可能不再竞争同一租约，应先停止原写实例，临时解除不是多写部署支持。

### 后续修复方向与验收条件

后续方案应首先确定可跨 Pod 连续使用的持久状态来源：经过目标环境验证的持久卷，或能支持事务、历史查询及租约协调的共享状态后端。接管应能区分完整历史、落后副本和全新状态，并显式报告恢复范围及无法确认的窗口；不能仅用可改写的 UUID 代替这些事实。

同时设计业务窗口的稳定写入身份、目标表幂等策略和防止过期写者继续提交的 fencing 机制。结合实际 ClickHouse 表引擎、物化视图与写入方式验证，不能只增加 query_id 或去重参数就承诺不重复。

关闭本遗留项前至少需要以下验收证据：

1. 同节点及跨节点替换 Pod，完整持久状态可延续，成功窗口不重放，UNKNOWN 仍保留核查。
2. 滚动更新、强杀、租约超时与网络分区时，不产生未受控的双写；验证已提交 SQL 的收尾行为。
3. 挂载空卷、落后备份、独立账本时能明确识别历史缺口，并按批准的恢复策略处理；不能用“进程启动成功”代替恢复成功。
4. 重复接管及恢复步骤可重入，对相同业务窗口的多次提交不会重复累计，且下游验收包含真实表引擎和依赖。
5. 目标持久存储的锁、同步、磁盘满与断连恢复经过验证；备份后已写入的窗口在恢复时得到核对。
6. 诊断同时展示当前任务进度、历史连续性和协调状态，三者不会混为一个 PASS；保留现有查询与执行审计。

本次代码测试只验证身份阻断已移除、旧元数据保留和原协调检查继续执行，不替代以上生产环境验收。

## DC-STATE-002

**问题：调测期间临时关闭启动配置差异与缺库阻断，持久状态及配置接续方案尚未完成。**

- 状态：未解决；2026-10-20 按用户要求临时关闭相关启动校验，并允许手动删除数据库后重新初始化。
- 优先级：高，影响配置升级、历史连续性与汇聚结果一致性。
- 范围：正常启动时的部署绑定、当前配置及 SQL 与保存快照的差异检查，以及初始化标记存在但数据库缺失的处理。
- 关联：[DC-STATE-001](#dc-state-001) 记录跨 Pod 状态连续性和重复写入问题；本项没有解决这些问题。

### 现场信息与判断边界

现场报错涉及当前配置与已有状态的差异，用户为继续调测要求先移除相关启动限制，并要求手动删除 DB 后可以重新初始化。此要求是临时处理策略，不代表旧配置与当前配置已核对一致，也不代表删除数据库能够恢复执行历史。

现场日志中的任务数量为 56，而当前仓库配置预期为 60，说明现场所用包、挂载配置与当前仓库之间存在需要核对的不一致。任务数量本身不能断定现场一定使用旧镜像，也不能据此还原旧账本的配置；后续需核对实际镜像摘要、包内任务定义、运行时配置挂载及 SQL 文件。

### 本次临时措施与保留边界

1. 正常启动不再仅因部署绑定不符，或当前配置及 SQL 与已保存的有效快照不同而拒绝启动；`--init-state`、`--run-once`、`--run-task` 和 `--resolve-instance` 对此同样临时放行，已有覆盖起点和每任务有效起点仍约束执行。原绑定、快照和执行历史保留，已有的无快照旧账本自动恢复流程保留。日志与诊断明确提示校验临时关闭，并关联本遗留项；诊断的差异为 WARN，匹配时可为 PASS，但均附 `binding_enforced=false` 和 `configuration_enforced=false`，不表示检查策略已恢复。
2. 初始化标记存在但数据库已被手动删除时，允许取得本地锁后重新创建状态库，不再由缺库检查阻断。残留的 SQLite `-wal`、`-shm` 和 `-journal` 文件移入状态目录内的 `.state.sqlite3.orphans.*` 目录保留，避免误用于新库；该目录不是已恢复的历史。诊断查询保持只读，不负责创建、修复或恢复数据库。
3. 保留同一物理账本的本地锁、临时 Redis 选主租约、续租及失租停止新派发。当前配置仍须能够有效加载，已有数据库的损坏、结构及必要状态完整性检查仍保留。
4. 本轮不自动执行数据库删除、不恢复旧数据库内容，也不根据缺失记录推定窗口成功或自动补算。配置迁移与历史恢复工具的明确操作边界，仍需与正常启动的临时放行区分。

删除 DB 后创建的是新账本。原成功记录、UNKNOWN、任务尝试、调度游标、就绪信号、配置审计和积压窗口不会自动恢复；默认启动从新初始化的覆盖起点开始处理，旧窗口不会因此补算。数据库外已经写入的业务数据仍然存在，新账本无法据此判断哪些旧窗口已完成。若后续扩大覆盖范围、恢复过旧备份或重新提交旧窗口，仍可能重复写入。

临时放行配置差异也不证明旧游标、待处理实例和当前任务定义兼容，不能把旧任务按新 SQL 执行的结果视为已经过迁移核验。历史实例的依赖解释应继续检查证据是否匹配，无法确认时明确说明，不凭当前配置重建旧事实。

调度时，已移除任务、窗口定义变化或早于任务有效起点的旧待处理记录会保留并跳过，输出 `PERSISTED_WINDOW_SKIPPED`，不再让这些记录阻止当前任务执行；旧游标按当前 cron 规则重新对齐。跳过的记录并未完成汇聚，后续仍需核查和处理。

既有初始化边界也需统一：无配置快照的旧账本中，`--init-state` 只检查原覆盖起点非空，未完整验证其时间格式；无效值可能得到 `INITIALIZED`，但正常启动和诊断仍会失败。初始化结果不能替代正常启动与诊断验证，本轮未扩展该旧路径。

### 后续修复方向与验收条件

1. 明确部署长期使用的持久状态来源，验证 Pod 替换、卷重新挂载、断电及落后备份恢复后的历史连续性；区分首次部署、人工重置与意外状态丢失。
2. 为配置与 SQL 变更设计可核对、可重复执行的接续过程，明确旧实例、游标、任务起点和新增或移除任务如何处理；恢复可验证的配置差异检查。
3. 结合真实 ClickHouse 表结构、写入方式和依赖，完善稳定业务窗口身份、目标端幂等及过期写者隔离，验证重复接管或恢复不会重复累计。
4. 记录并展示新账本的覆盖起点、历史缺口、配置校验关闭状态和当前协调状态；正常启动成功不能代替恢复成功或结果一致性的验收。
5. 补齐同配置重启、增删任务、SQL 变更、手动删 DB、完整状态目录丢失、损坏库、锁冲突及租约丢失等场景验证，并完成现场 56 / 60 个任务差异核对。

关闭本遗留项前，应有目标部署环境的持久化与幂等验收证据，并确定重新启用检查的策略；本轮本地回归只验证临时放行和保留检查的行为。

## DC-STATE-003

**问题：共享状态冲突记录只有审计字段，暂时没有处置状态和清理入口。**

- 状态：已记录，待补运维处置流程。
- 优先级：中，影响冲突记录的长期维护，不阻断接管。
- 范围：`mirror_conflicts`、`--status` 和 `--diagnose` 展示的本地 SUCCESS 与共享终态差异。

当前行为会保留每个实例最近一次冲突，并展示本地状态、共享状态、双方 query ID 和发现时间。运维需要核对 ClickHouse 结果与 query 执行证据后，在外部工单或值班记录中登记处置结论。记录保留用于审计，清理和“已处理/已忽略”状态需要后续补充。

验收条件包括新增处置状态、按实例记录处置人和时间、保留原始冲突证据、提供受控查询与归档入口，并验证重复接管不会产生无界重复记录。
