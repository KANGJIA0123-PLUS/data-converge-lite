# Data Converge：可验证恢复的时序汇聚服务

## 项目主张

面向已有 ClickHouse 指标汇聚链路，在不改业务 SQL、不新增基础设施的条件下，用持久化派发协议解决一个实际问题：服务中断后，如何知道哪些任务可以安全继续，哪些任务必须核对。

参赛方向是工程创新与业务价值。竞赛名称和评分细则尚未提供，以下是可据实论证的价值，而不是获奖保证或全球首创声明。

## 问题从哪里来

汇聚服务维护本地任务状态，ClickHouse 执行外部写入，两者没有共同事务。客户端断线或进程退出时，“没有收到成功”不代表“没有写入”。统一自动重试可能重复计算，统一转人工又会让确定未提交的任务也进入核对队列。

本项目给出可检查的界限：准备阶段不允许发送；提交派发意图后才允许调用运行器。恢复依照已提交事实，而不是按异常文字、固定重试次数或猜测表名决定。

## 架构表达

设计语言统一为“窗口、依赖、准备、派发、结果、证据”。每个术语都有明确接口与持久化事实，详见 [架构与时序图](architecture.md)。

| 层次 | 负责什么 | 明确不负责什么 |
| --- | --- | --- |
| 应用用例 | 初始化、运行、人工处置、写入准入与生命周期 | 不实现 SQL 或数据库事务细节 |
| 调度与领域契约 | 窗口、依赖、预算、准备和派发顺序 | 不猜测 ClickHouse 表结构 |
| 事务账本 | 实例状态、检查点、尝试历史、事件原子保存 | 不假装与 ClickHouse 共同提交 |
| 外部适配器 | ClickHouse 执行、Redis 信号和租约 | 不擅自将未知结果变成可重试 |
| 只读诊断 | 恢复计划、历史、事件投影及操作建议 | 不在查询时恢复、清理或提交任务 |

## 本轮新增贡献与原有基础

| 能力 | 原有基础 | 本轮贡献 |
| --- | --- | --- |
| 状态连续 | SQLite 实例、游标、就绪事实 | 复用同一账本，无第二套批次状态源 |
| 崩溃恢复 | 遗留 RUNNING 统一 UNKNOWN | PREPARED 有证据可恢复，已派发仍保守核对 |
| 尝试历史 | query_id 级历史及人工处置 | 准备不计次，派发时计次，避免恢复虚增预算 |
| 可观测性 | 日志、状态、历史诊断 | 同事务有序事件、恢复分类预览及 JSONL 续读 |
| 验证 | 状态、资源释放等回归测试 | 真实子进程退出 + 独立持久接收记录 + 两次回放 |

## 可以争取评审认可的四个理由

**一、问题与机制能够对应。** 自动恢复的依据是“提交前的持久化证明”，可以说明为何安全、在哪个边界必须停止。方案没有以“自动重试次数更多”替代一致性设计。

**二、工程取舍清楚且落地成本可控。** 使用现有 Python、SQLite、ClickHouse 和 Redis，保留 56 个任务及业务 SQL，不引入新的运行服务。新增检查点与事件共用原事务，不增加两个状态源的对账负担。代价是每次执行多一次账本提交和新增审计空间，需如实测量目标环境开销。

**三、故障表现可以现场复现。** 演练在提交边界用真实子进程退出，接收端独立记录每一次调用且不做去重。准备中断可以继续；已接收但未记账的任务不会被自动重放；成功后再调度也不会增加接收数。原始 JSON 包含预期、观测、query_id、事件和环境。

**四、业务价值有可量化的路径。** 安全自动恢复减少一类人工核对，结构化事件减少查找分散日志的步骤，未知结果隔离降低误重跑风险。现阶段已经能证明协议行为，成本节省需采集生产频率与人工耗时后计算，不填虚构收益。

## 已有实测

| 强制退出位置 | 恢复后的处理 | 两次回放后的接收总数 | 能证明什么 |
| --- | --- | ---: | --- |
| 准备后、派发前 | 自动排队并执行成功 | 1 | 未提交工作可自动继续，准备中断不计次 |
| 派发意图后、实际接收前 | UNKNOWN，停止自动重放 | 0 | 接受保守判断，避免把没有完成证据当成没有副作用 |
| 独立接收端已记录、完成记账前 | UNKNOWN，停止自动重放 | 1 | 客户端中断后不盲目重复提交 |
| 成功记账后 | 保持 SUCCESS | 1 | 重启及重复调度不增加提交 |

本表来自 [原始演练数据](evidence/recovery-drill-2026-10-18.json)，方法和测试结果见 [验证报告](evidence/recovery-verification-2026-10-18.md)。这是离线协议验证，未执行真实 ClickHouse SQL，不证明集群吞吐、分布式事务或跨节点容灾。

## 业务价值如何采样

| 指标 | 采集方法 | 可用的计算方式 |
| --- | --- | --- |
| 自动恢复的准备中断量 | 统计 RECOVERED_UNSUBMITTED，关联后续成功 | 分母用全部恢复候选量，展示自动恢复覆盖范围 |
| 人工核对工时 | 工单记录开始/结束时间、实例及 query_id | 安全自动恢复实例数 × 同类实例历史核对耗时中位数 |
| 重复提交量 | 服务事件与 ClickHouse 端记录关联 | 按实例窗口比较实际提交数与预期数，单列人工授权重试 |
| 排障证据准备耗时 | 固定问题集，用旧日志检索和新诊断分别操作 | 同一场景、同一人员交叉测量，报告样本量和分位数 |
| 新协议运行成本 | 相同任务量、磁盘、并发下采样 | 比较派发延迟、账本写入量和空间增长，不混入 SQL 计算差异 |

金额收益还需要实际人工或资源单价。没有现场数据时只展示指标定义、采集方法和离线证据。

## 五分钟答辩顺序

1. **问题（40 秒）**：展示“数据库可能已写入，但客户端没收到成功”的崩溃窗口，说明盲重试和全人工的成本。
2. **架构（60 秒）**：用时序图解释准备与派发两个提交点；强调只在有未提交证明时自动恢复。
3. **演练（100 秒）**：运行离线演练，展示准备中断、已接收未记账两个对照场景，查看接收次数与事件。
4. **工程证据（60 秒）**：展示事务回滚、旧账本兼容、只读诊断、重试预算和现有失败项的基线记录。
5. **业务价值与下一步（40 秒）**：给出人工核对和排障时间的采样方案，明确生产集群验收与容量评估尚需完成。

## 对边界问题的回答

- **是否 exactly-once？** 不是。SQLite 与 ClickHouse 没有共同事务；方案扩大可证明安全的自动恢复范围，保留未知结果核对。
- **为何不查 query_log 后全自动处理？** 日志可延迟或缺失，缺失不能证明未执行。未来可针对明确部署契约增加证据适配器，不能通用推断。
- **为何不用批次数据库？** 当前实例、游标和依赖已经定义进度，复用同一事务可减少状态漂移。
- **为何派发后但未接收仍 UNKNOWN？** 因为本地没有足够证据确认远端未执行，这是协议明确接受的保守窗口。
- **是否已经适合生产和比赛交付？** 核心协议有可复现证据；正式发布前仍要处理平台脚本已有失败、完成真实集群和容量验收，并补齐比赛要求的生产业务数据。
