# 提前测试汇聚与跨周期有限等待

状态：用户于 2026-10-21 批准开始开发，并要求默认开启、所有跨周期默认额外等待 5 分钟。
基线：e25a077；下述接口随本轮实现交付。

## 目标与范围

用户需要提前运行尚未结束的小时、日等窗口，使用已有源数据测试下游功能。
结果必须写入现有目标表，采用现有业务 SQL、窗口起点和维度口径。
正式调度到期后仍须实际执行并覆盖测试结果，DWS 和 ADS 均不能因提前成功而被跳过。
正常跨周期汇聚等待上游完整，但只等待可配置的有限时间；上游提前齐全则提前放行，
到截止时间仍不齐就按已有数据执行，并保留缺失证据。

本次不新增业务表或字段，不重写业务 SQL，不修改打包、启动或部署文件。
提前结果用于功能测试，不宣称是完整周期的真实统计；沿用正式 SQL 的速率分母等口径。
不新增定时刷新提前结果、不把已有数据移动到完全未来的时间范围、不生成未来业务数据。

## 设计选择

采用“相同目标表、独立提前执行记录、正常正式实例不变”。
只放开未来时间限制会使正式实例提前 SUCCESS，从而在正常触发时被去重，不能采用。
将提前结果写到另一套表不满足本次测试目的。全局取消 SUCCESS 去重会破坏正常调度。

提前执行成功只证明一次测试 SQL 执行成功。正式成功仍由正式执行记录证明。
正常调度保持单写者，先完成正常调度，再处理一个手工队列条目；不新增并发写同窗口。

## 提前汇聚入口

拟新增 `--backfill --preaggregate`，仍使用现有 `--task` 或 `--all-tasks`、
`--from`、`--to`、`--dry-run`、`--request-id` 和 `--backfill-status`。

```bash
bash /opt/its/data-converge/bin/start_data_converge.sh \
  --backfill --preaggregate --task task_model_instance_day_dws \
  --from '2026-10-21T00:00:00+08:00' \
  --to '2026-10-22T00:00:00+08:00'
```

规划时使用一次固定的当前时间，将完整逻辑窗口分为：

- 已结束窗口：保留普通补算语义，已成功窗口仍需 `--recompute` 才重算。
- 已开始、未结束窗口：记为 PREAGGREGATE，参数仍是完整逻辑窗口。
- 尚未开始窗口：不创建写入条目；预览和提交结果明确列出省略数量及原因。
- 没有可执行窗口：明确报错。单任务边界仍须对齐，现有窗口数量上限仍适用。

不传 `--preaggregate` 时，现有禁止未来结束时间的规则保持不变。
新请求可再次刷新提前结果；同一 request-id、同一计划只执行一次。
每条队列记录的执行类型在提交时固定，不能因排队跨过窗口结束而变成正式补算。

提前提交与执行前都检查以下条件：

1. 窗口已经开始，实际派发时尚未结束。
2. 窗口起点不早于 coverage_start 和该任务生效起点，未被历史隔离。
3. 当前配置的未来 Cron 确实会生成同一正式窗口，且调度游标尚未越过该触发。
4. 任务、SQL、目标和清理策略仍匹配提交时快照。
5. 没有同窗口正式执行、正式成功，或尚未核实的提前执行结果。

不满足自动正式覆盖范围时拒绝提前写入，明确报告原因；不暗中修改覆盖起点或游标。
排队到窗口结束后的提前条目标记 SKIPPED 并记录到期原因，不再写入目标表。
已经开始的提前 SQL 可以跨过窗口结束；主线程等其完成后才执行正式任务。
如果执行结果变成 UNKNOWN，先执行下述结果核查保护。

## 提前记录、下游测试与恢复

在主状态库新增独立 `preaggregate_attempts`，以 item_id 去重，并记录 canonical
instance_id、任务、窗口、配置版本、query_id、派发时间、状态、错误及人工核查信息。
其登记和完成必须在主库事务中持久化，之后才同步 backfill 队列结果。
队列同步失败通过 item_id 取回原结果，不重新执行 SQL。

提前执行不能调用会更新正式 task_instances 的 begin_backfill/finish 路径，
不能推进正常调度游标，也不能在正式 get_status 中返回 SUCCESS。
正式调度到期后仍创建原来的正式实例，运行同一 SQL runner，覆盖同一目标窗口。
提前执行 DWS 和 ADS 时均使用这一规则，因此正式 ADS 也会重新等待正式 DWS 并覆盖。

提前模式的同周期依赖可使用同批次成功的提前条目；未在本批次选择的上游，
可使用同窗口、同配置版本的最近一次提前成功，或已有正式 SUCCESS。
若本批次选中上游且失败，不回退到更早成功；跨批次也不能越过较新的失败或 UNKNOWN
使用旧提前成功。到期 SKIPPED 不视为提前成功；普通补算 SKIPPED 需要核对正式 SUCCESS。
正式任务的依赖只认可正式账本状态。
提前模式及显式历史补算不增加跨周期等待，不等待历史 DWD 信号，使用执行时已有数据。

主库中的提前 RUNNING 在崩溃恢复时变为 UNKNOWN，不自动重放。
同窗口存在尚未核查的提前 RUNNING/UNKNOWN 时，正式 claim、人工补算与人工确认
不得绕过它发起冲突写入或直接认定正式成功。此保护不受跨周期等待超时豁免。

拟提供 `--resolve-preaggregate ITEM_ID --resolution success|retry --note TEXT`，
采用与现有人工处理相同的独占状态库要求。操作者先确认对应清理与汇聚操作均已结束，
记录核查依据；success 只确认提前执行成功，retry 只解除已核实的未知结果保护，
允许显式新请求或到期正式任务覆盖，两者都不写正式 SUCCESS、不立即重跑旧条目。
原始 UNKNOWN 历史保留，另记核查结论；正式汇聚仍须真实执行。

## 跨周期等待配置

配置放在 app_config.yaml 的 scheduler 中，避免为纯等待策略改变任务数据身份：

```yaml
scheduler:
  cross_period_wait_enabled: true
  # 正常任务到达 Cron 触发时间后，额外等待跨周期上游的最大秒数。
  cross_period_wait_seconds: 300
  # 按任务覆盖全局值；未列出的任务继承全局。
  cross_period_wait_overrides:
    task_model_instance_day_dws: 300
```

默认开启，默认 300 秒，包含小时、日等所有跨周期任务；旧配置省略字段也采用该默认值。
关闭 cross_period_wait_enabled 后立即停止跨周期等待；不删除已经保存的截止时间，
重新开启时沿用原截止，不重新计时。0 秒明确表示不等待。
只接受非负整数，拒绝 bool、负数、浮点、字符串及未知任务覆盖项。
范围覆盖所有跨周期关系，如五分钟到小时、小时到天、天到月。
同周期依赖继续要求成功；DWD 就绪、租约、重试次数及 UNKNOWN 保护不变。

等待策略视为运行调度设置，不加入既有业务 manifest、TaskDefinition 或 binding。
修改时长不迁移任务生效起点，不清空历史，不重置现有排队窗口的等待时限。
随正常服务加载配置生效；不新增动态热加载。

## 等待与超时规则

对每个正式正常调度窗口枚举其跨周期直接上游实例，并与同周期硬依赖分开保存/展示。
完整性以正式上游 SUCCESS 判断，不以表中是否恰好有 24 行判断。
不存在、失败、未知、隔离或仅有提前成功的上游都计为尚未完整。

正常调度入队时，在同一事务登记独立 `cross_period_waits`：
instance_id、原 Cron 触发时间 scheduled_due_at、wait_seconds 快照、deadline_at。
重复入队不能修改这些值。截止时间为原 Cron 时刻加实际等待秒数，不能用 data_end
代替，也不能从每次检查/服务重启的当前时间重新计时。

| 例子：日任务原定 00:10，额外等待 300 秒 | 行为 |
| --- | --- |
| 00:10 上游完整 | 执行 |
| 00:10 上游不完整 | 进入跨周期等待，不消耗 SQL 重试次数 |
| 00:13 上游齐全 | 下一次调度检查放行，不等满五分钟 |
| 00:15 仍有缺失 | 记录告警和缺失证据，放行后用已有数据执行 |
| 00:12 服务重启 | 原截止仍为 00:15 |
| 00:30 服务才恢复 | 已超过原截止，不重新等十分钟 |

“放行”只解除跨周期等待，SQL 开始时间还取决于轮询、并发容量及其他硬条件。
不使用阻塞 sleep 等五分钟；每轮正常调度重新判断。
单轮执行耗时较长时，判定时间应随实际经过时间前进，避免使用批次开始时的旧时间。

旧库中尚未处理的实例若没有等待记录，只有在存在可信来源证据时才使用持久化的原
触发时刻；不能根据后来修改的 Cron 推测旧触发，也不采用来源不明或由 backfill
写入的 scheduled_time=data_end。无法确定原触发时刻时，记录兼容诊断并保留旧实例
原有的跨周期立即执行语义，不新加等待或永久阻塞。配置 0 秒不要求推断原触发时刻。
历史补算不新建或消费正常等待预算；正常失败后的自动重试沿用原等待记录。

超时执行后的正式 SUCCESS 仍表示 SQL 执行成功，不表示上游已经完整。
本次不增加“上游晚到自动再次重算”；后续修复使用现有显式 `--recompute`。
这一选择与“提前测试结果必须由正式调度覆盖”是两个独立行为。

## 日志与查询

默认 INFO 显示提前执行开始/结束、窗口、query_id、执行类型和未来正式触发时刻。
默认 WARN 显示跨周期等待超时，包含原触发、截止、缺失总数、状态分布与最多 100 个
缺失实例；同时标明是否截断。等待期间不每五秒重复告警。

等待放行决策与缺失证据独立持久化，并与正式 query_id 关联，SQL 成功后仍可查询。
`--inspect-instance` 保留同周期 dependencies，增加 cross_period_wait 和提前记录摘要，
显示 WAITING/READY/TIMED_OUT、截止时间、缺失数量和人工核查是否未完成。
`--backfill-status` 的文本和 JSON 都区分提前执行与正式补算，标明提前成功不等于正式完成。
历史/恢复查询应能找到提前 UNKNOWN，不要求用户手工查询 SQLite；所有诊断保持只读。
旧库缺少新增表时返回该能力无记录，不由诊断命令建表。

## 覆盖方式与兼容性

保持现有同窗口先清理后 INSERT 的覆盖方式，不承诺两步之间原子可见。
SQL 错误和连接中断仍可能使目标窗口暂时为空，必须保留失败/UNKNOWN 证据。
本次功能测试需求不引入临时业务表、分区交换或新的发布体系。

新增状态表通过受控写服务初始化；现有普通补算队列和旧记录仍可读取，
缺少 execution_kind 的旧条目解释为正式补算。新请求版本明确，旧程序不能把新提前
请求误当作普通补算；部署说明要求同一版本 CLI 与服务配套使用。
提前状态未核查或仍有待正式覆盖的结果时，配置迁移、写服务启动和普通执行入口均须
核验相关任务的定义与覆盖条件。不能静默移除任务、改变窗口/SQL/Cron、把任务生效
起点移到待覆盖窗口之后，或越过应执行的游标，使覆盖承诺丢失。不能只依赖显式迁移
命令约束，因为当前程序也允许直接修改配置后启动。拒绝失去覆盖保障的配置启用，
诊断入口仍可只读查看原因；不把无关任务的普通等待时长调整当作业务身份变更。

## 验收与实现边界

1. 提前执行确实使用原 SQL、原目标和原完整逻辑窗口，正式实例未被提前记成功。
2. 同一窗口 DWS/ADS 提前测试后，正式 Cron 均真实执行并覆盖，目标不重复累加。
3. 到期旧提前条目不写入；重复 request-id、崩溃后队列同步均不重复执行 SQL。
4. 提前 UNKNOWN 可见、可核查，未核查时正式写入受保护；核查不冒充正式成功。
5. 不可自动覆盖的 coverage、任务生效起点、游标、Cron 或隔离窗口明确拒绝。
6. 正常等待在齐全时提前结束、截止时放行；重启、重复入队和失败重试不延长时限。
7. 默认开启/300 秒、关闭与重新开启、0 秒、任务覆盖、非法配置和旧配置默认值分别验证。
8. 同周期硬依赖、DWD、租约与原重试限制不因超时而失效。
9. 验证 DST、月长、日边界和不同 Cron 分钟，不能写死每天 24 个小时实例。
10. 超时后成功仍有缺失审计；诊断读取前后数据库内容不变。
11. 队列、主库事务和恢复使用现有测试框架；用隔离的本地 ClickHouse 验证先后覆盖，
    不连接生产数据库。遵守函数 50 行限制，运行相关回归和 git diff --check。

主要改动位于 backfill、state、dag、scheduler、config/application、runtime 与 diagnostics。
更新 app_config.yaml、命令帮助及 backfill/architecture/diagnostics 文档。
业务 SQL、ClickHouse 表结构和公司部署框架保持现有接口。
