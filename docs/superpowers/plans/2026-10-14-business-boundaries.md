# 业务资源边界重构实施计划

**目标：** 恢复用户确认的可靠性改动，明确连接、账本资源和写入资格的所有权，保持现有业务行为与公司构建兼容。

**架构：** 应用用例继续由 `Application` 组织，`RuntimeDependencies` 提供明确工厂。Redis 连接资源独立于队列消费与选主；SQLite 资源管理通过组合服务于 `StateStore`，业务状态与审计继续共用事务。

**技术：** Python 3.12、现有 redis-py、SQLite、标准库 Protocol/上下文管理器；无新依赖。

**设计依据：** [业务架构](../../architecture.md)、[可靠性边界](../../reliability.md)，以及本轮用户授权的目录与业务代码重构。

## 不变量

- 不改公司构建、部署、启动脚本、业务 SQL 或镜像目录约定。
- 保留 `data_converge.main`、现有 CLI、配置路径和公开导入。
- 函数及测试含装饰器不超过 50 行；测试留在原目录。
- 同一物理账本接管；不把本次变更描述为数据库 exactly-once。

## 实施与验收

- [x] 恢复可靠性提交，保留之后的路径诊断修复；运行恢复相关用例。
- [x] `state/database.py` 提取 `LedgerDatabase`，`state/store.py` 保留事务和兼容入口。验证只读不建表、连接失败不遗留锁、关闭顺序及审计回滚。
- [x] `infrastructure/redis/` 统一连接、认证、凭据与加密资源；`create_connection(config)` 返回有 `client`、`sentinel_clients`、`identity`、`close()` 的独占连接资源。队列源、租约和诊断分别组合自己的连接；验证连接失败清理与兼容认证。
- [x] `coordination/` 分离窄接口、准入、守卫与工厂，保留原公开导出；验证租约释放先于连接关闭、失租不提交新工作。
- [x] 更新架构说明，运行业务回归与公司字节码构建验收；保留并说明现有 7 项启动/探针基线失败。
- [x] 独立审查改动范围和兼容性。

集成方式：验证完成后，正常提交并推送 main，不改写已有历史。

## 审查重点

1. `--help` 和离线诊断不能加载或调用 Redis/平台 SDK。
2. SQLite 先关闭、文件锁后释放；只读诊断不能抢写锁或升级库。
3. 任务状态与执行历史同一事务，禁止审计内部单独提交。
4. 续租线程结束、释放租约后才能关闭 Redis/Sentinel 连接池。
5. 新目录必须经过原构建的纯 `.pyc` 导入验证，测试不得进入镜像。

## 验证结果

- 完整回归：691 项通过、1 项跳过、7 项既有启动/探针测试失败。失败仍是公司脚本的固定路径权限处理与探针提前返回，与本次业务目录重构无关；不放宽断言。
- 原公司脚本在临时副本构建的纯 `.pyc` 可加载全部 52 个任务，运行 XMS 子进程，且不包含测试。
- 临时、无挂载的真实 Redis 实例验证：独立连接池、队列确认、租约竞争、同账本身份接管、释放后租约删除；验证后移除实例。
- 无配置文件、无 Redis/DSF/PSF/Crypto 的环境中 `--help` 可用。
- 独立代码审查未发现需要阻止合入的 P1/P2 问题；函数行数和差异空白检查通过。
